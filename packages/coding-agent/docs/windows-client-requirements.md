# Windows 客户端产品需求片段

本文档记录基于 Pi agent core 构建 Windows 桌面客户端时已经达成一致的产品方向。本文是后续详细需求规格的工作稿片段。

## 产品定位

本产品是面向企业内部业务用户的本地 Windows 桌面智能体客户端。客户端以 Pi agent core 作为智能体内核，通过图形化界面提供模型配置、工作区选择、文件操作、工具执行、skills、企业接口和业务工作流编排能力。

目标用户是非技术企业用户，包括产品经理、法务、财务以及其他专业业务人员。客户端不能要求用户理解命令行、代码仓库结构或智能体内核实现细节。

## 第一版优先场景

第一版优先支持产品经理使用的 OCR prompt 优化工作流。如果该工作流和其他场景存在能力设计冲突，以该工作流为优先。

用户选择一个项目文件夹作为 workspace。智能体可以在该 workspace 及其下级目录中读取、新建和编辑文件。涉及文件编辑时，应尽量优先在复制后的副本上操作，而不是直接修改原始文件。

核心闭环如下：

1. 用户提供卡证图片。
2. 用户定义需要 OCR 提取的字段。
3. 智能体结合具备视觉能力的大模型、workspace 内知识文件、prompts 和 AGENTS.md 等规则说明，撰写或优化提取 prompt。
4. 智能体通过已配置的 tools 或 skills 调用外部 OCR 或验证接口。
5. 用户可以执行单次验证，也可以执行批量验证。
6. 智能体将提取结果与人工提供的标准答案进行比对。
7. 智能体计算准确率并分析失败样本。
8. 智能体提出 prompt 优化建议。
9. 每一轮结束时都需要用户确认是否满意，再决定继续优化或最终定稿。

输出结果应包括最终 prompt、验证结果、准确率报告、失败样本分析和迭代记录。

## 第二优先场景

第二优先场景是法务合同审查。用户指定一个或多个待审合同后，智能体基于合同审查规则、知识文件和审查清单，完成合同文本抽取、合同类型识别、条款类型识别、审查事项匹配、高风险或不一致结果复查，并形成最终审查结果。

合同审查输出应尽量写入合同副本中，优先使用修订格式或清晰的审查批注表达结果。

## 配置与扩展能力

客户端必须支持灵活配置 prompts、AGENTS.md 风格知识、skills、tools 和企业内部外部接口。未来版本需要预留子智能体能力。

Skills 和 tools 应以业务能力的方式呈现，而不是直接暴露为脚本或命令行命令。典型业务能力包括 OCR 验证、批量样本评估、prompt 版本管理、合同文本抽取、合同审查清单执行和报告生成。

## 权限模型

默认 workspace 权限模型如下：

- 智能体可以读取用户选择的 workspace 内文件。
- 智能体可以在用户选择的 workspace 内新建文件。
- 智能体可以在用户选择的 workspace 内编辑文件。
- 智能体应优先编辑文件副本，而不是直接编辑原始文件。
- 智能体可以执行 bash 命令。
- bash 命令不需要逐条让用户确认。
- 批量接口调用不需要逐次让用户确认。
- 外部网络请求不需要单独逐次授权。
- 允许调用企业内部 API。
- 允许读取 workspace 外部文件，但应经过用户明确确认或由用户主动选择授权。

客户端不应把 bash 命令或原始命令细节直接暴露给业务用户。界面应展示业务动作、执行进度、执行结果和必要风险说明。

## 审计日志

每一次 tool 调用都必须记录审计日志。审计日志至少应包括：

- 时间戳。
- 会话 ID。
- 任务或工作流 ID。
- Workspace 路径。
- Tool 或 skill 名称。
- 业务动作名称。
- 输入摘要。
- 输出摘要。
- 读取、新建或编辑的文件。
- 网络请求目标或企业 API 目标。
- 是否批量执行。
- 成功或失败状态。
- 失败时的错误信息。
- 关联的迭代轮次。

由于智能体在任务级授权后可以自动执行命令、调用 API 和访问文件，审计日志必须从第一版开始实现。

## 账号与数据模式

第一版不需要云端账号体系。本产品初期是面向企业用户的本地个人智能体。配置、会话、日志、prompts 和生成产物应存储在本地，除非未来需求明确增加云同步或企业集中管理能力。

## 智能体内核与更新策略

第一版客户端应内置固定版本的 Pi agent core。用户不需要手动安装或升级 Pi。

架构上必须预留未来由用户主动更新智能体内核的能力。未来当接口层兼容时，可以允许用户选择兼容的内核版本进行更新。客户端后续应支持内核版本检测、兼容范围校验、用户选择更新、回滚到内置版本以及更新失败恢复。

## 客户端技术栈

客户端技术栈确定为 Electron、React 和 TypeScript。

该选择优先考虑研发速度、可维护性、界面快速迭代、与现有 TypeScript 生态的贴合度、本地进程管理、桌面文件选择、日志能力和未来自动更新能力。已知取舍是安装包体积和运行时内存占用会高于更轻量的桌面框架。

## 初始架构方向

客户端应把 Pi agent core 视为由适配层封装的本地内置引擎：

```text
Electron UI
  -> Agent adapter
    -> Embedded Pi agent core
```

适配层必须隐藏内核进程和协议细节，避免 UI 业务逻辑直接依赖内核实现。这样第一版可以保持简单，同时为未来内核替换、内核升级或协议兼容变更预留空间。

## 协作与后续需求格式

后续详细需求建议按工作流拆分，并至少包含以下字段：

- 场景名称。
- 目标用户。
- 输入文件。
- 知识文件。
- 外部接口。
- 需要的大模型能力。
- 允许的工具。
- 禁止的操作。
- 用户确认点。
- 输出文件。
- 验收标准。
- 失败处理。
- 审计记录。
