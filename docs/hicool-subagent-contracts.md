# HICOOL 专业 Subagent 业务与运行合同

## 1. 共同定义

三个专业 Subagent 使用同一套运行语义：

- 由 MTClaw Function Router 自动选择或编排，用户不需要手动 `@` 或切换智能体。
- 由 pi-agent 创建隔离子任务并执行，不由 wrapper 脚本模拟智能体。
- 模型、Tool、MCP、Skill、知识和权限来自 Staix 中对应子智能体配置。
- 输出结构化事实、来源、判断、限制和错误，供当前智能体回答模型生成最终回答。
- 不把缺失数据、模型推断或查询失败伪装成已核验事实。

术语不变量：`enterprise_due_diligence`、`legal_research` 和 `civil_litigation_document_generation` 是 Subagent 稳定角色；`delegate_to_subagent` 是协议层委托入口；QCC、HTTP API、MCP、浏览器、文件和 Shell 才是该子智能体可以选择的 Tools。

当前产品配置已固定三个稳定角色，并允许在 Staix 子智能体编辑器中登记是否接受 MTClaw 自动路由。通用 `delegate_to_subagent` 桥接会根据该配置启动隔离 pi-agent RPC 子任务；是否能够形成真实业务成果仍取决于 Router、子智能体模型及其已绑定能力的实际联通验证。

## 2. 通用调用合同

以下字段是目标协议的逻辑结构，不代表已经确定的 TypeScript 类型或 MTClaw JSON schema：

```json
{
  "task_id": "task-uuid",
  "session_key": "stable-session-key",
  "subagent": "enterprise_due_diligence",
  "objective": "核验某企业主体并识别重大风险",
  "input": {},
  "context_refs": [],
  "constraints": {
    "deadline_ms": 60000,
    "require_sources": true
  }
}
```

通用结果：

```json
{
  "task_id": "task-uuid",
  "subagent": "enterprise_due_diligence",
  "status": "success",
  "summary": "结构化任务摘要",
  "facts": [],
  "findings": [],
  "sources": [],
  "limitations": [],
  "errors": [],
  "metrics": {
    "started_at": "ISO-8601",
    "ended_at": "ISO-8601",
    "duration_ms": 0
  }
}
```

`status` 至少支持：

- `success`：完成任务且关键证据可用。
- `partial`：部分数据或能力不可用，但已明确缺口。
- `needs_confirmation`：实体、审查立场或授权存在关键歧义，需要用户确认。
- `failed`：无法形成可用业务成果，返回可审计错误。
- `cancelled`：用户或上游取消任务。

## 3. 企业主体核验与风险尽调

### 稳定名称

`enterprise_due_diligence`

### 业务目标

确定用户所指企业主体，核验其工商身份，识别经营、信用和司法风险，并形成有来源、有查询时间、有不确定性说明的尽调结果。

### 输入

- 企业名称、统一社会信用代码或其他主体线索。
- 可选地域、法定代表人、历史名称等消歧条件。
- 查询深度和关注风险类型。
- 可选交易背景或合同相对方身份。

### 必须完成的步骤

1. 判断输入能否唯一识别企业主体。
2. 发生重名或信息冲突时返回候选项并请求确认，不擅自选择。
3. 核验企业基础登记状态和关键身份字段。
4. 查询获授权数据源覆盖的经营、信用和司法风险。
5. 区分原始数据、规则归类和模型判断。
6. 为关键事实保留数据源、查询时间和定位信息。
7. 给出风险等级、理由、数据缺口和建议的后续核验事项。

### 可复用能力

- 已在 Staix 配置的 QCC MCP/CLI 或获授权 API。
- HTTP/MCP、浏览器、知识、文件和 Shell 能力。
- 主体核验与尽调报告 Skill。

这些能力由 pi-agent 调用；API Key 和授权信息不写入 `functions.jsonl` 或 wrapper。

### 验收场景

- 唯一企业名称能够返回正确主体和统一社会信用代码。
- 重名企业触发消歧，不混合不同主体数据。
- 注销、吊销或经营异常状态被明确标记。
- 数据源无结果时返回 `partial` 或 `failed`，不生成虚假记录。
- 接口超时、权限不足和限流均有清晰错误与审计记录。

## 4. 法规和类案研究

### 稳定名称

`legal_research`

### 业务目标

围绕明确的法律问题检索有效法规、司法解释和相似案例，形成可追溯、可复核、说明适用边界的研究结论。

### 输入

- 法律问题、争议焦点或事实摘要。
- 法域、审级、地区和目标时间范围。
- 可选案由、关键词、主体类型和研究深度。

### 必须完成的步骤

1. 将用户问题拆分为可检索的法律争点。
2. 生成并迭代法规和案例检索式。
3. 标记法规效力层级、公布/施行时间和当前有效性。
4. 对案例进行事实相似度、争点相似度和裁判观点归类。
5. 区分法律依据、裁判参考和模型分析。
6. 输出支持与不支持结论的材料，避免只选择单一方向证据。
7. 提供来源、定位、查询时间和适用限制。

### 可复用能力

- 获授权的法规库、案例库、HTTP/MCP 和浏览器能力。
- Staix 知识配置、文件工具和法律研究 Skill。

### 验收场景

- 能区分法律、行政法规、司法解释、指导性案例和普通裁判文书。
- 已失效或修订法规不会被当作当前有效依据而无说明地使用。
- 类案结论能够回溯到具体争点和来源。
- 检索无结果时明确说明检索范围与缺口。
- 来源不可访问或内容冲突时返回限制说明，而不是补写不存在的引文。

## 5. 民事诉讼文书生成

### 稳定名称

`civil_litigation_document_generation`

### 业务目标

理解用户提供的案件材料，判断诉讼地位和当事人类型，选择对应的官方文书模板，先生成可核对的文本预览，经用户确认后输出排版好的 DOCX。

第一阶段只支持自然人民事起诉状、法人民事起诉状、自然人民事答辩状和法人民事答辩状。

### 输入

- 起诉或应诉的任务意图。
- 自然人或法人的当事人类型。
- 文本、图片、扫描版 PDF、文本型 PDF 或 DOCX 案件材料。
- 当事人信息、诉讼请求或答辩意见、事实与理由、证据、法院和案件信息。
- 可选的输出文件名。

### 必须完成的步骤

1. 优先直接读取文本、DOCX 和文本型 PDF；仅在图片或扫描版 PDF 无法直接提取文本时调用 OCR。
2. 判断用户属于起诉方还是应诉方，以及文书主体属于自然人还是法人；无法可靠判断时先询问用户。
3. 将材料整理为当事人、诉讼请求或答辩意见、事实与理由、证据、法院、案号和签署信息等结构化字段。
4. 从四种固定模板中选择且只能选择一种。
5. 不得编造姓名、证件号码、金额、日期、案号、法院、证据或法律事实；缺失内容统一标记为 `[待补充：字段名]`。
6. 先输出文本预览和待补充清单，等待用户确认。
7. 用户确认后调用 `generate_civil_litigation_document`，在当前工作区的 `generated-documents` 目录生成 DOCX。
8. 返回模板类型、文本预览、DOCX 绝对路径和仍待补充的字段。

### 可复用能力

- `ocr_text_extract`：只负责图片和扫描件文字提取。
- `extract_civil_case_material`：确定性读取 DOCX、文本型 PDF、TXT 和 Markdown；文本型 PDF 无可用文本层时返回需要 OCR，不通过 Shell 工具猜测文件内容。
- 模型：负责材料理解、字段整理和模板选择。
- `generate_civil_litigation_document`：只负责按照固定结构生成预览和 DOCX，不负责补造事实。
- 默认不绑定浏览器、企业查询或法律检索能力；确需法律研究时，由上级智能体另行委托 `legal_research`。

### 验收场景

- 四种模板均能正确选择并生成。
- 图片材料能够通过真实 OCR 提取文字。
- 缺失信息能够稳定显示为待补充项，不被模型补造。
- 未经用户确认不生成最终 DOCX。
- 生成的 DOCX 可由 Word 或兼容软件正常打开，且只写入当前工作区。
- OCR、材料解析或文书生成失败时明确返回失败原因和已完成部分。

## 6. Router 路由边界

| 用户意图 | 首选 Subagent | 可能编排 |
|---|---|---|
| 核验企业身份、工商状态、司法或经营风险 | `enterprise_due_diligence` | 无 |
| 查询法律依据、法规有效性、相似案例或裁判观点 | `legal_research` | 可补充企业主体背景 |
| 生成民事起诉状或答辩状、整理案件材料 | `civil_litigation_document_generation` | 可由上级智能体另行编排法规类案研究 |

Router 不应把以下请求注册为 MTClaw 专业 Subagent：普通文件读写、通用 Shell、网页打开、工作区选择、会话管理和模型配置。这些继续是 pi-agent/Staix 的通用能力。

## 7. 运行与安全不变量

- 子智能体只获得任务所需能力，不能默认继承全部敏感能力。
- pi-agent 的用户确认、文件边界和浏览器授权不能由 wrapper 绕过。
- wrapper 从 stdin 读取一个 JSON 请求，向 stdout 输出一个 JSON 结果；诊断信息写 stderr；退出码 `0` 表示协议级成功，非 `0` 表示执行失败。
- `success` 不代表法律结论无需人工复核，产品输出始终定位为专业人员辅助材料。
- 日志保存路由、模型、工具、耗时和来源，但必须对凭据和敏感字段脱敏。
- 取消、超时、子智能体失败和上游模型失败必须分别记录，不能统一伪装为正常回复。
- 子智能体的模型和工具步骤必须回传父会话过程时间线，并明确标记为子智能体步骤；不能只展示一次 `delegate_to_subagent` 完成事件。

## 8. 竞赛验收证据

每个 Subagent 至少准备：

- 5 个正常业务样例。
- 2 个实体或意图歧义样例。
- 2 个能力失败或数据缺失样例。
- Router 自动命中记录。
- pi-agent 子任务与工具执行记录。
- 当前智能体回答模型调用记录。
- 来源、耗时、失败回退和最终业务成果。

跨 Subagent 连续演示必须在同一主会话中完成，并证明每轮均由 Function Router 自动选择或编排，而不是用户手动指定智能体。
